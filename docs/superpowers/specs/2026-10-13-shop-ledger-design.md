# PersonalFinancesPro 首版设计

日期：2026-10-13

状态：用户已确认本设计；当前正在通过本机 OpenDesign 规划 UI 和制定分阶段实现计划，尚未初始化 Flutter 应用。

## 1. 已确认的决定

- Flutter 开发，支持 Android 与 iOS。
- 使用 Clean 架构，并参考 Flutter 官方架构建议与 Effective Dart。
- 本地优先：SQLite 保存业务数据，支持手动备份、恢复；不做账号系统、后台或自动跨设备同步。
- 自定义 DeepSeek API Key，支持对话生成账单，用户确认后保存。
- 创建公开仓库 `https://github.com/nedhuohuo/PersonalFinancesPro`，使用 MIT 许可证。
- 产品暂用名 PersonalFinancesPro；应用标识使用 `dev.nedhuohuo.personalfinancespro`。

## 2. 产品边界

这是多网店的“平台外经营收支账本”，不是电商订单系统、完整会计软件或进销存系统。

首版记录厂家采购和货款、配件和包装采购、外部快递充值、退货问题件通过其他渠道出售的收入，以及其他平台外经营收支。

拼多多等平台已记录的订单销售、订单退款、平台佣金、内部推广费和内部运费不重复录入。判断依据是业务来源，不是付款工具。平台提现也不作为本账本的新销售收入。

不做平台 API 对接、订单导入、库存、问题件剩余数量追踪、语音识别、票据 OCR、多人协作、个人生活账本或自动资金对账。

平台外现金净额不能称为店铺利润。没有完整平台收入、退款、库存和销售成本数据，不展示净利润。

## 3. 首版功能

### 3.1 基础资料

- 店铺：新增、改名、停用；停用后保留历史账单。
- 账单归属：选择一个店铺或“公共经营”。首版不做跨店自动分摊。
- 资金账户：银行卡、微信、支付宝等自定义名称；用于标记收付款来源，不计算真实账户余额。
- 交易对象：厂家、买家、快递服务商，可维护名称；首版不要求联系方式。
- 收支分类及二次销售渠道：内置常用项，支持新增、改名、停用。
- 已有账目引用的资料不允许物理删除。
- 启用时可为厂家录入期初欠款；不产生启用当日的现金支出。

### 3.2 通用现金账单

- 字段：稳定 ID、业务日期、收入/支出、金额、店铺、分类、资金账户、交易对象、备注、录入来源、创建及更新时间、作废状态。
- 业务日期可手选，默认设备本地的当天；业务日期以 `YYYY-MM-DD` 保存，审计时间以 UTC 保存。
- 新增、编辑、作废、恢复及筛选；作废记录不参与统计。
- 作废和恢复保留变更记录，不物理删除账目。
- 按日期、店铺、分类、交易对象筛选；搜索备注。
- 普通账单金额必须大于零；修正使用明确的关联冲销/退款操作，不使用不明负数。
- 首版以人民币为唯一货币。
- 不在首版提供账户间转账和真实账户余额；账户标签不能被误用为完整资金流水。

### 3.3 厂家采购与付款

- 采购单：厂家、店铺、日期、商品明细、数量、单价、应付给厂家的运费、备注。
- 数量为正整数；单价以整数分表示。配件散装或其他复杂计价可直接记通用支出。
- 采购金额 = 商品明细合计 + 应付给厂家的运费。
- 单独付给物流的运费另记支出，不计入对厂家的欠款。
- 采购单和付款是不同数据：建立未付款采购单不产生现金支出。
- 采购时付款、分次付款均生成关联的现金支出；待付款 = 有效采购金额 - 有效付款净额。
- 本次付款不得超过该采购的待付金额；供应商预付款不在首版实现。
- 支持单独登记期初欠款和其后付款；欠款减少与现金支出在同一事务中保存。
- 已有有效付款的采购单不能直接作废；先通过明确的撤销或退款流程处理关联付款，防止丢失往来记录。
- 厂家退货区分“减少未付货款”和“退回已付货款”：前者调整应付，无现金收款；后者同时减少有效采购额和付款净额，并生成关联的退款收入。
- 混合退货可拆成上述两种金额处理；每次操作保持 `0 <= 付款净额 <= 有效采购金额`。
- 退款不得超过可退已付金额，应付调整不得超过未付金额；保留原单和调整原因。
- 厂家退款单独分类为退款回收，不计为商品销售收入。

### 3.4 问题件二次销售

- 定义：网店退回的问题件，通过平台外其他渠道出售后获得的收入。
- 记录原店铺、业务日期、商品描述、数量、实收金额、收款账户、买家、出货渠道及问题说明。
- 不要求导入原平台订单，也不自动估算成本或库存。
- 实收金额作为收入；运费、手续费作为独立关联支出，不能把净额伪装成销售收入。
- 收入与同时录入的费用原子保存；费用的付款账户不能自动猜测为收入账户。
- 支持查看本次净回收金额 = 有效收入 - 关联费用；不标为利润。
- 首版不处理二次销售的分期应收款，按实际收款记账。

### 3.5 快递充值

- 建立快递预付账户，可录入期初余额。
- 充值产生一笔现金支出，同时增加快递预付余额。
- 实际扣费减少预付余额，是快递消耗记录，不产生第二笔现金支出。
- 可手动记退款：减少预付余额，同时产生现金收入。
- 扣费及退款不能使余额小于零；期初值、充值、消耗和退款均保留记录。
- 作废历史记录若导致余额不合法则拒绝，要求先修正其后相关记录。
- 余额命名为“账本记录余额”，不声称与快递服务商实时对账。
- 未录入消耗时只展示充值和记录余额，不推算快递成本。

### 3.6 看板及导出

- 所选期间的平台外现金收入、现金支出、现金净额。
- 按店铺、收支分类、厂家、二次销售渠道汇总。
- 采购金额、已付款净额、待付款分别展示，不把采购金额再次计入现金支出。
- 二次销售收入及关联费用后的净回收金额。
- 快递充值、实际消耗和账本记录余额。
- 期间统计排除作废数据；退款单独展示，并可查看现金收入总计的构成。
- CSV 导出当前筛选下的现金账单，正确转义字段，防止文本字段成为电子表格公式。

### 3.7 备份与恢复

- 完整 JSON 备份：格式版本、导出时间、业务资料、账单、采购与调整、快递记录、审计记录；金额均为整数分。
- 备份不包含 API Key、会话内容或其他凭据；CSV 是报表，不是完整备份。
- 系统文件选择器导入备份；通过系统分享导出到用户选择的位置。
- 恢复前明确提示“替换当前账本”，要求先导出当前账本并确认。
- 首版仅支持完整替换，不合并两个设备的账本。
- 校验格式版本、类型、金额范围、唯一 ID、关联完整性和余额约束后，在数据库事务中恢复。
- 文件大小上限 20 MiB；未知格式版本或不合法内容拒绝导入，原数据不受影响。
- 备份含敏感经营数据且不自动加密，导出前提醒用户自行保管。首版不上传自有云端。
- 应用数据库和凭据排除在系统自动云备份之外；跨设备迁移使用显式手动备份，不承诺卸载后可恢复。

## 4. AI 记账

### 4.1 配置

- DeepSeek 默认 Base URL：`https://api.deepseek.com`，默认模型：`deepseek-chat`。
- 可编辑 API Key、模型和兼容 Chat Completions 协议的 Base URL；不承诺兼容所有提供商扩展。
- Base URL 定义为接口前缀，规范化后追加 `/chat/completions`；拒绝 query、fragment、userinfo 和非 HTTPS URL。
- Key 使用系统 Keychain/Keystore 支持的安全存储；非敏感模型及地址可保存在本地设置。
- 编辑地址时提示 Key 的接收主机，保存前确认；不跟随携带凭据请求的重定向。
- 测试连接、清除 Key、关闭 AI；无 Key 时手动功能完全可用。
- 不把 Key 写入仓库、日志、数据库备份或报错界面。

### 4.2 流程

1. 用户输入文字；会话只保存在当前页面内存，不自动持久化。
2. 首次联网前说明当前服务商和即将发送的内容，取得同意。
3. 仅发送当前任务的文字、必要的本地资料候选和日期上下文，不发送完整账本。
4. 模型生成受限结构的数据或缺失字段问题；默认不创建陌生店铺、交易对象和分类。
5. 不明确的店铺、账户、日期、金额、交易方向必须补问或在草稿中由用户选择。
6. 本地解析和校验金额、类型与关联，计算总额；不信任模型的计算结果。
7. 展示可编辑草稿；确认后使用与手动记账相同的领域操作保存。
8. 多笔同次草稿原子保存；每个草稿具有一次性提交 ID，连点或重试不重复入账。

- AI 首版可生成通用收支、采购与同时付款、问题件二次销售及费用、快递充值草稿。
- 修改、删除、恢复已有账目及复杂退款调整只走明确的手动流程，AI 无直接写入权限。
- 对可能重复的日期、金额、店铺和对象提示核对；不自动丢弃可能合法的重复交易。
- 默认请求超时 30 秒，支持取消；鉴权失败、额度不足、限流、网络故障和无效输出给出可理解提示。
- 超时或失败不自动再次提交账单；保留用户输入供手动录入。
- 模型输出不执行代码、不拼接 SQL、不接受文件路径或任意工具调用。
- 首版不做自由式 AI 查账；看板和筛选查询使用数据库计算，避免把账本发给模型。

## 5. 架构与工程规范

### 5.1 目录与依赖方向

```text
lib/
  app/                      # 应用入口、路由、主题、依赖装配
  core/                     # 必需的金额/日期规则、数据库及通用基础设施
  features/
    catalog/                # 店铺、账户、交易对象、分类、渠道
    ledger/                 # 现金账单、采购付款、二次销售、快递预付
    dashboard/              # 本地统计
    backup/                 # 导出、校验、恢复
    ai_bookkeeping/         # API 配置、对话及草稿
```

每个功能按实际需要包含 `presentation/`、`domain/`、`data/`，不为不存在的实现创建空目录。

- `domain`：纯 Dart 业务模型、仓库契约及复杂 Use Case，不导入 Flutter、SQLite、HTTP 或插件。
- `data`：仓库实现、数据库映射、HTTP 和安全存储，依赖领域契约。
- `presentation`：页面、Widget、ViewModel，依赖领域契约，不直接访问数据库或 HTTP。
- `app` 在组合根装配具体实现；使用构造器注入，不使用全局 Service Locator。
- 复杂的采购付款、退款、关联收支、备份恢复等放在 Use Case；简单查询不机械增加转发类。
- 仓库契约是用户要求的 Clean 边界，不为每个 DTO、方法或数据库表添加额外接口。

### 5.2 技术选择

- Flutter stable，使用项目级 SDK 固定版本；不沿用当前旧 master 预发布版。
- Flutter 自带 `ChangeNotifier` 管理 ViewModel，`provider` 负责依赖注入。
- `go_router` 管理四个主入口及详情页面。
- `sqflite` + `path` 存储本地关系数据、事务与 schema 迁移。
- `http` 发起 AI 请求，`flutter_secure_storage` 保存凭据。
- `file_selector` 导入备份，`share_plus` 导出报表与备份。
- 使用 SDK 自带 JSON 支持及手写的小型映射；首版不引入代码生成、通用 BaseRepository、EventBus 或微服务。
- 创建时固定可兼容的稳定版本，应用提交 `pubspec.lock`；具体 SDK 版本在环境阶段确认并写入项目配置和 README。

### 5.3 业务数据约束

- 金额以整数分存储和计算，不用 `double` 处理金额；单笔及汇总金额不得超过 `9,000,000,000,000,000` 分，越界拒绝操作。
- 金额输入从十进制字符串精确解析，最多两位小数；超出精度要求用户改正，不静默舍入。
- 币种固定 CNY；每笔业务使用稳定 ID，保存关联与审计时间。
- 数据库启用外键和事务；关联采购、付款、收入及费用、快递余额变动不得部分保存。
- schema 版本化，升级不删除旧账本；迁移失败停止打开写入路径，不使用清库兜底。
- 逻辑实体包括基础资料、现金账单、采购及明细、付款和采购调整、期初欠款、二次销售详情、快递预付事件及审计记录。
- 审计记录保留操作类型和必要的变更快照，不记录密钥或 AI 会话。

### 5.4 UI 与错误处理

- 四个主入口：首页、账本、AI 记账、设置。
- Material 3、中文优先；尊重系统明暗主题、安全区和文字缩放。
- 金额输入、主操作和图标有明确标签，不仅靠颜色区分收入与支出。
- 保存过程中阻止重复提交；失败保留编辑内容，不展示虚假成功提示。
- 本地账本无网络也能工作；AI 关闭或失败不影响账单、统计和备份。
- 用户自行保存导出的备份；卸载应用会丢失未备份的数据，设置页明确提醒。

### 5.5 测试与持续集成

- 采用 `dart format`、`flutter_lints`、`flutter analyze`，遵循 Effective Dart。
- 使用 Flutter 自带测试工具验证领域规则、仓库和 ViewModel；Widget 测试覆盖主要页面及确认流程。
- 核心用例：金额精度和上限、采购与付款不重复计支出、部分付款及退款、二次销售收入与费用、快递充值与消耗、作废恢复、无效备份原数据不变、AI 无效输出及重复确认。
- HTTP 使用 fake client，不在测试或 CI 中使用真实 Key，不付费调用模型。
- 数据库迁移及恢复有实际数据库的集成验证；真实设备或模拟器验证安全存储和文件操作。
- GitHub Actions 在 push/PR 执行格式检查、静态分析和测试；主分支执行 Android debug 构建。
- iOS 在可用 macOS 工具链上执行无签名构建；不把无签名构建等同于可发布安装包。
- 正式签名、App Store/Google Play 上架和费用不在首版自动化范围内。
